# 面试材料包：Enterprise Support Agent V2

本材料基于当前 V2 代码、已保存的评估结果和用户在 WSL 的实测反馈。订单、政策均为虚构演示数据。回答时应同时说明结果和限制。

## 项目定位与协作表达

这是从 Dify 低代码 Agent 向 Python 代码级 Agent 工程转变的学习项目。项目目标是理解用户请求如何经过 API、业务数据、LangChain 组件、LangGraph 流程、评估和部署，而不是罗列框架。开发采用 Codex 技术负责人/主力开发者、我负责学习理解与运行观察的协作方式；面试时要如实讲明 AI 辅助范围，只讲自己能解释的代码、验证结果和技术边界，不把未实现的生产能力说成项目成果。

## 3 分钟项目介绍

> 我做的是一个企业售后 Agent 的代码化重构和工程学习项目，也是我从 Dify 低代码开发转向 Python 代码级 Agent 工程的第二个项目。V1 是 Dify 项目，V2 复用原政策、模拟订单和 45 条评估规格，同时把 RET-01 和 QUA-01 作为标注来源的 V2 补充规则单独维护。这个项目要让我理解从请求入口、数据访问、Agent 编排、RAG、评估到部署的完整链路，而不是单纯展示技术栈。
>
> 后端用 FastAPI 提供 `/chat`、订单查询和健康检查，SQLite 存订单，LangGraph SQLite checkpoint 保存需要人工处理的中断状态。请求进入后先由确定性路由分类：订单查询在 SQL 层同时按订单号和租户号过滤；政策咨询走 LangChain RAG，使用 SiliconFlow 的 `BAAI/bge-large-zh-v1.5` 做向量化、Chroma 做本地检索，再由 `Qwen/Qwen2.5-7B-Instruct` 基于证据生成回答并检查引用编号。
>
> 权限和写操作不交给模型决定。改地址、改状态等写请求会拒绝；退款请求先检查当前租户下订单是否存在，再由 LangGraph interrupt 暂停。批准后只写入演示状态 `approved_demo`，没有退款工具，也不修改订单。Checkpoint 支持重启后恢复。
>
> Agent 对 35 条有可映射路由标签的用例为 35/35；修复前是 30/35。标注订单参数 8/8，独立临时 SQLite 工具调用 9/9，标注的 outcome 和订单字段分别 6/6、5/5，调用前后数据库不变。RAG 复用 V1 的 45 个案例，其中 36 个有 required evidence 标签。Hit@4 为 100%，平均 Recall@4 为 86.6%，完整召回所有必要证据的比例是 72.2%。所以至少命中一份证据不等于证据完整，我保留了 POL-10 等多证据漏召回案例。用户报告从干净克隆运行全量 pytest 53 项通过（18.39 秒）；WSL Docker 验收 health 200 且 11/11 用例通过。两者为不同环境的独立证据。
>
> 这是单机工程演示，不是生产权限系统。公开 Demo Bearer token 只映射固定 user/tenant，不是真实身份认证；客户端 `X-Tenant-ID` 被忽略。SQLite checkpoint 不适用于多实例高可用。Top-2/4/6/8 检索对照已完成：Top-8 提高证据完整召回，但生成对照和人工抽查没有证明答案更好；同模型 LLM 自评有误判，因此默认仍为 Top-4，语义评分还需独立复核。

## 10 分钟架构讲解

### 0:00–1:00：场景和目标

V1 已有售后政策、订单数据和 Dify 流程。V2 将业务规则放到可读、可测的 Python 服务中，形成用户请求、路由、数据/检索、状态管理、评估和部署的完整链路。固定订单 1001 是 `demo-a` 的定制商品质量问题案例。RET-01 和 QUA-01 是带 V2 来源标注的新规则，不冒充 V1 原文。

### 1:00–2:30：API 和 SQL

FastAPI 提供 `/health`、`/orders/{order_id}`、`/chat` 和审批演示端点。Pydantic 校验请求，Swagger 提供接口操作入口。SQLite 有 `tenants` 和 `orders` 两表：`tenants.tenant_id` 是主键；`orders.order_id` 是主键，`orders.tenant_id` 是外键并有索引；金额用整数分。查询采用参数化 SQL：`WHERE order_id = ? AND tenant_id = ?`。旧订单归入 `legacy-demo`，不猜测缺失客户归属；订单 1001 属于 `demo-a`。

目前没有 `users` 表或单独的 Agent 任务日志表：请求轨迹输出为结构化 JSON 日志，持久化审批状态放在 checkpoint。真实用户和租户身份需要由认证系统提供，不能从 Header 直接信任。

### 2:30–4:00：权限和路由

`route_request` 用确定性规则分流订单查询、政策问答、写请求、退款审批和澄清。授权不是 LLM 的工作。订单工具只读并强制 tenant 条件；其他租户查不到订单时只返回未找到语义。退款请求进入演示审批；非退款写请求拒绝。`X-Tenant-ID` 只是租户隔离演示参数，不是认证。

### 4:00–5:45：LangChain RAG

当前 12 份政策形成 12 个短块，metadata 保存来源 ID、版本等信息。Embedding 使用 SiliconFlow `BAAI/bge-large-zh-v1.5`，本地向量库是 Chroma；聊天模型为 `Qwen/Qwen2.5-7B-Instruct`。Retriever 输出政策来源、内容和距离，再与问题一起交给 Prompt/Chat Model，最后检查输出引用编号是否属于这批证据。没有证据时不调用生成模型。`citations_valid` 只验证引用 ID，不代表每条自然语言结论都被证据蕴含。当前未校准距离阈值。

### 5:45–7:00：LangGraph 和 HITL

State 保存单轮问题、租户、意图、订单号、订单或政策证据、答案、引用结果、错误摘要和审批状态。Node 负责路由、只读查询、检索/生成、拒绝、澄清及审批；Conditional Edge 决定后续路径。退款订单通过租户校验后触发 `interrupt()`，SQLite saver 保存 thread；决定经 `Command(resume=...)` 恢复。批准只标记 `approved_demo`，不修改订单。SQLite checkpoint 是本机演示方案，不能描述为生产多实例状态服务。

### 7:00–8:15：评估和故障注入

Agent 路由评估在 35 个有可映射预期路由的案例上计分，并分别报告有标注的工具参数、工具调用、outcome 和订单字段；分母不同，不能合并成整体成功率。RAG 评估在 36 个有 evidence 标签的案例上统计 Hit@4、平均 Recall@4 和完整召回比例；9 个无标签案例不评分。Hit@4 是“至少一份期望证据”，Recall@4 是“找回多少期望证据”。no-write 专项只有 4 个明确确定性案例。测试用假 Embedding/Chat 模型和 monkeypatch 注入数据库、Embedding 故障；真实模型超时等场景仍未完整模拟。

### 8:15–9:15：Tracing 和 Docker

每个 HTTP 请求有 `X-Trace-ID`；结构化日志记录 HTTP/Node 开始和结束时间、耗时、路由、订单参数与状态摘要、召回来源及距离、引用检查、审批状态和异常类型。用户输入只记录最多 500 字符的预览，常见 Key、Bearer token、邮箱和手机号会脱敏；模型完整答复不入日志。WSL 从 `/opt/project2` 构建，以避开 `/mnt/d` 遇到的 BuildKit 权限问题；`/mnt/d/project_2/data` 挂载到容器 `/app/data`，并由 D 盘持久保存。Dockerfile 分层安装第三方依赖和源码，并使用 TUNA pip 源及较长下载超时，降低重复构建时间和网络超时概率。

### 9:15–10:00：结果和下一步

已验收 Docker health 200、订单查询、紧邻中文的“查询订单1001”、退款待审批、POL-06 答案引用及无错误日志；最新日志中订单节点耗时约 16.9ms、政策生成约 756ms，POL-06 distance 0.625 是该次查询最相似来源。多/非法订单号、隐私索取和提示注入修复已由用户同步并在 WSL 容器验收，断言式阶段 6 脚本全部通过。Top-2/4/6/8 检索对照和 Top-4/Top-8 生成探索已完成；后者同模型自评存在误判，Top-8 还出现政策冲突回答，所以默认仍为 Top-4。剩余质量工作是独立复核、生成提示强化和真实模型超时/限流故障演练；生产化还需真实身份与审批人权限、生产级持久化和安全监控。

## 20 个技术面试问题与参考回答

1. **为什么从 Dify 重构？** 为了实践 API、SQL、状态编排、测试、评估和容器部署，同时复用 V1 资产；V2 运行不依赖 Dify。
2. **LangChain 和 LangGraph 分工是什么？** LangChain 负责文档/模型组件和 RAG 链；LangGraph 负责有状态业务节点、条件路由、中断与恢复。
3. **为什么用 Graph 而不是普通函数？** 简单问答不一定需要 Graph；本场景需要可见的分支和 HITL checkpoint，Graph 让节点状态和恢复边界清楚。
4. **State 保存什么？** 单轮问题、租户、意图、订单号、订单、证据、答案、引用状态、错误类型与审批状态；没有保存对话历史。
5. **为什么不用 LLM 判断权限？** 模型输出不可作为授权依据；由 API 注入租户上下文、由业务逻辑路由、由 SQL 强制租户过滤。
6. **租户隔离在哪里执行？** `fetch_order` 参数化查询在 `WHERE` 同时匹配订单号和 tenant ID；不匹配统一返回无结果。
7. **`X-Tenant-ID` 决定租户权限吗？** 不决定。当前服务端从 Bearer Demo token 映射固定 user/tenant，忽略客户端伪造 Header；生产环境仍需真实认证、授权和密钥管理。
8. **审批通过为什么仍是只读？** Graph 只把状态变成 `approved_demo`；没有退款服务工具，也没有订单写 SQL，批准前后订单不变。
9. **Checkpoint 解决什么问题？** 保存 interrupt 时的 State，让审批后能恢复同一 thread；也验证应用重启后待审批状态仍在。
10. **为何使用 SQLite checkpoint？** 单机演示部署简单；多实例并发和高可用需替换为支持生产负载的持久化方案并处理锁、恢复和迁移。
11. **为什么一个政策文件一个 chunk？** 当前 12 份文档短，完整保留上下文与规则例外；长文需重新切块，并用同一评估集衡量取舍。
12. **Embedding 与 Chat Model 的职责分别是什么？** Embedding 将文档和查询向量化用于语义相似检索；Chat Model 根据召回上下文组织回答。
13. **Chroma distance 如何解释？** 是检索距离分数，当前越低通常越相似；未校准阈值，所以它用于观察，不作为硬性拒答条件。
14. **引用有效是否代表答案正确？** 否。只检查引用 ID 出现在召回集合；事实是否受证据支持需用人工或事实级判分。
15. **Hit@4 与 Recall@4 的区别？** Hit@4 只要求至少命中一份预期来源；Recall@4 计算所需来源命中比例。当前 Hit 100% 但完整证据召回仅 72.2%。
16. **为什么只评 36/45？** 只有 36 条有明确 `required_evidence` 标注，其余 9 条不能在无标签情况下据此评分。
17. **主要 RAG Bad Case 是什么？** 例如专票时限问题召回 POL-09，却缺 POL-10 人工协助边界。Reranker 无法把没进入候选集的来源找回来。
18. **模型/Embedding 出错如何响应？** 节点记录异常类型并返回安全提示；单测注入异常验证路径。云服务真实超时和限流场景还需补故障模拟。
19. **为什么没用多 Agent、Redis、Kubernetes？** 当前单一业务流程不需要多个 Agent 协作，SQLite 支持本地小规模状态；这些组件会增加复杂度，当前问题也未要求它们。
20. **离生产最近的三项工作是什么？** 真实认证和 tenant 授权、审批人 RBAC/审计、生产级持久化；随后补足语义评估、检索质量和运行安全策略。

## 5 个故障案例深挖

| 案例 | 现象与证据 | 修复/验证 | 可展开的问题 |
|---|---|---|---|
| 1. 中文和订单号无空格 | `查询订单1001` 被 `\b` 边界判断误分流为 clarify | 改用 ASCII 订单号左右边界；API/路由用例和 WSL 容器都通过 | 为什么不能完全取消边界？如何避免从长 token 中截出假 ID？ |
| 2. 越租户读取 | `demo-a` 与 `legacy-demo` 查同一个订单得到不同授权结果 | SQL 固定绑定两个查询参数；测试确认其他租户不可读 | 为什么统一 not-found，比返回“订单属于别的客户”安全？ |
| 3. 多政策证据漏召回 | Top-4 的 KB-09/NA-02 命中 POL-09，却漏掉 POL-10 | Top-2/4/6/8 同集对照显示 Top-8 完整证据率提高至 97.2%；但 Top-8 生成回答未证明更优，默认保留 Top-4 | 这是召回还是排序问题？为什么 rerank 不一定能修？ |
| 4. 数据库/Embedding 服务失败 | 故障注入使依赖节点抛异常 | 返回安全提示和异常类型，避免泄露内部异常；数据库与 Embedding 初始化失败有测试 | 如何区分超时、鉴权失败与空结果？重试会有什么副作用？ |
| 5. Docker 内路径错到安装目录 | pip 安装后向量库指到 `site-packages`，政策召回 0 条 | `_resolve_env_path` 按工作目录解析数据库、checkpoint、向量库；最终 WSL RAG 引用通过 | 为什么数据目录不应相对 Python 模块文件？如何测试容器路径？ |

另有测试覆盖无订单号澄清、未知引用检测、空检索不调用模型、checkpoint 重启恢复、重复审批冲突。真实 Chat API 超时、Embedding 超时/限流、checkpoint 文件损坏、Docker 缺少 Key 的故障还未全部验证，不应描述为已覆盖。

## LangChain 与 LangGraph 的一句话区分

LangChain 解决“文档、检索和模型调用链怎么组成”；LangGraph 解决“业务状态在节点间怎么走、在哪里中断、之后怎样恢复”。
