# RAG 证据支撑边界评估与加固计划

更新：2026-11-24。本文是阶段提案；当前只完成只读审查，未改变 RAG 答复、数据、索引或部署。

## 目标

评估并降低一种具体风险：答案中出现了本次检索的合法政策编号，但所引用内容并不支持该句事实。重点是区分“来源编号存在”和“该来源支持该结论”，并在证据不充分时标记或澄清。首轮不引入大型评测框架、LLM-as-a-Judge 或全局相似度阈值，也不承诺自动证明一般自然语言蕴含。

## 当前实现与审查证据

1. `src/support_agent/rag/retrieval.py::retrieve_policies` 使用 `build_policy_retrieval_query()` 扩展问题，并调用 Chroma `similarity_search_with_score(..., k=top_k)`；Top-K 默认配置为 4。结果含来源编号、标题、原文和距离，但生产回答不以距离阈值拒答。
2. `src/support_agent/rag/answer.py::generate_answer_from_evidence` 对非空证据调用 Prompt/模型或窄范围硬约束。`citation_check_passed` 只检查引用编号是否属于本次检索来源集合。
3. `tests/test_rag_boundaries.py::test_unrelated_nonempty_evidence_can_still_produce_a_valid_citation` 明确记录：物流证据可被模型用于生成退款主张，来源编号校验仍会通过。这是缺口特征测试，不是安全测试通过。
4. `find_explicit_evidence_conflicts()` 只检测移除单个“不/没/未”后完全相同、且命中主题锚点的句子；它不是一般语义矛盾检测器。
5. OOS-v2 答复和证据已归档；这 15 条数据已观察且含已知风险案例，不能再称为盲测。45 条原始开发集及其评分流程必须保持不变。

## 建议分阶段实施

### A. 人工标注证据归属数据（先审后跑）

- 新建独立数据文件，不修改原 45 条开发集、OOS-v1 或已观察的 OOS-v2。
- 目标约 15 条，覆盖充分支持、部分支持、无关但有合法引用、关键数字/承诺无依据、适用条件缺失、阶段/范围混淆、资料缺失应澄清，以及证据正文含指令样式内容。
- 每例标注问题、预期回答要点、相关政策编号、支持原句/段落、不可推出的主张、预期行为和类别。正向事实必须基于真实政策；“无依据”项须指出政策没有规定该结论，不能伪造政策。注入场景只使用明确标识的合成夹具，不写入政策文件或 Chroma。
- 先提交候选问题与证据标注供用户审核；审核前不调用新一轮真实模型、不向外部发送新数据。

### B. 独立审计运行器与报告

- 只读复用当前 Chroma、Embedding、Top-K=4、回答 Prompt 与配置模型；不重建或写入向量库。
- 保存回答、事实主张清单、每项主张对应的候选来源/原文片段、拒答/澄清行为和来源编号校验结果，以便人工复核。
- 首版以人工 gold 标注和明确规则筛查为准，不把规则匹配或同模型判断称作语义准确率。无法稳定匹配的主张标为 `needs_human_review`，不自动判为有依据或无依据。
- 检索指标沿用 Hit@4 / Macro Recall@4 并单独报告；答案支撑项报告 claim 级人工标签 supported / unsupported / partial / abstain 的数量与审核分母。Bad Case 沿用 DATA、CHUNK、RETRIEVAL、GENERATION、BUSINESS、ABSTENTION。
- 每次运行生成 Markdown 与逐案例 JSON；和 45-case 开发集及既有 OOS 结果分开。

### C. 低风险行为加固（依据评估结果另行提案）

- 首轮不改生产行为；继续保留空召回、明确冲突和现有窄政策约束。
- 对审计发现的高影响、可复现问题，先补回归测试和逐项修复提案。对无法确定语义支撑的回答优先增加审计标记或澄清，不用模糊距离阈值自动拒答，不做全局 Prompt 重写。
- 若后续确需改变答案路径，须完成新测试、人工抽样审核和全量 pytest，再按既有 WSL 流程部署验收。

## 预期变更面

方案批准后，预计新增 `data/evaluation/grounding/` 候选案例、`tests/grounding/` 评估代码和独立报告。首阶段不改 `answer.py`、`answer_constraints.py`、FastAPI API、政策、Chroma、SQLite、Docker 或 WSL 部署。评估若发现可复现问题，再单独列出生产路径改动与影响。

## 验收标准

1. 原 45 条、OOS-v1、OOS-v2 文件不被修改；每个数据集独立报告。
2. 案例的正向事实可回链到政策原文；无答案与注入夹具明确标识。
3. 单测覆盖完整支持、部分支持、无关合法引用、未支持主张和拒答/澄清的计分行为。
4. Mock 结果标为单元测试；只有真实 Chroma/模型运行才记为真实运行，且不声称盲测或语义准确率。
5. 逐案例 JSON 保留问题、实际答复、检索证据、claim 级审核标签和失败原因；Markdown 列出分母、分类及代表案例。
6. 全量 pytest 通过。若后续修改答复行为，再由用户按 WSL 流程验收。
